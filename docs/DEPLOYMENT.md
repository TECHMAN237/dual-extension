# Deployment

In production the backend runs on **Render** (free plan) and the extension uses that server by default. The knowledge base (Duala words and their sources) is a **file versioned in Git**, `data/knowledge/douala.json`, shipped with the code. There is no database. Nobody needs to run `pnpm dev:backend` to use the extension: that command is only for development.

| Mode | Backend | Storage | Extension default |
| --- | --- | --- | --- |
| Production | Render web service `douala-ai-backend` | `data/knowledge/douala.json` from the deployed commit, in memory (`ALLOW_EPHEMERAL_STORAGE=true`) | `VITE_DEFAULT_BACKEND_URL` from `apps/extension/.env.production` |
| Development | `pnpm dev:backend` on http://localhost:8787 | the same file, written back on changes (commit it) | http://localhost:8787 (build without `.env.production`, or change it in Settings) |

## 1. Storage: the knowledge base lives in Git

- **Source of truth:** `data/knowledge/douala.json` at the repository root (see `data/knowledge/README.md` for the format and licences). The backend resolves the path from the repository root, so it is found both locally and on Render, where the server starts in `apps/backend`. `LOCAL_KNOWLEDGE_FILE` can point elsewhere (absolute, or relative to the repository root).
- **At startup** the backend loads the file: sources, imported dictionary entries (all `pending`) and the interface terms.
- **Changing it:** run an ingestion (`pnpm ingest:site …`, `pnpm ingest …`) or edit the file locally, check `git diff`, then commit and push. Render redeploys and the server loads the new file. The file is written in a stable order (sorted by id, 2-space indentation) so diffs stay readable.
- **On Render** writes are still possible (admin approvals, accepted corrections, usage counters). They live in memory, and in the deployment's copy of the file, until the next restart, sleep or deploy, when the free disk is wiped. **This is intended:** a lasting change must be made in the repository. That is why `render.yaml` sets `ALLOW_EPHEMERAL_STORAGE="true"`; with `NODE_ENV=production` the backend refuses to start without it (unless Supabase is configured).
- **Supabase (not used).** The Supabase code and `supabase/migrations/` are kept as a possible future option for shared, persistent writes. Nothing in the normal setup needs a Supabase account, and `render.yaml` sets no Supabase variable. To switch one day, create a project, run `supabase/migrations/0001_initial.sql`, set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` on Render, and remove `ALLOW_EPHEMERAL_STORAGE`.

## 2. Backend on Render

`render.yaml` (a Render *Blueprint*) describes the service:

| Setting | Value |
| --- | --- |
| Plan | `free` |
| Node | `NODE_VERSION=22` (latest Node 22.x on Render) |
| Build | `npm install -g pnpm@10.28.0 && pnpm install --frozen-lockfile && pnpm --filter @douala-ai/backend... build` |
| Start | `cd apps/backend && node dist/index.js` |
| Health check | `/api/health` |
| AI | `AI_PROVIDER=openrouter`, `AI_MODEL` / `AI_FAST_MODEL=google/gemma-4-31b-it:free`, `AI_FALLBACK_MODEL=google/gemma-4-26b-a4b-it:free`, `AI_BASE_URL=https://openrouter.ai/api/v1` |
| Secret you type in the dashboard (`sync: false`) | `AI_API_KEY` (OpenRouter key) |
| Storage | `ALLOW_EPHEMERAL_STORAGE="true"`: knowledge base from `data/knowledge/douala.json`, no Supabase |
| Generated by Render | `ADMIN_API_TOKEN` (protects `/admin/` and `/api/admin/*`) |
| CORS | `CORS_ALLOWED_ORIGINS=chrome-extension://egmamnfapihdpbmnamooaabbafmncpbh` |

**Why not Corepack.** The build installs pnpm with `npm install -g pnpm@10.28.0` instead of `corepack enable && corepack prepare pnpm@… --activate`. The Corepack bundled with older Node 22 releases verifies downloads against a hard-coded list of npm registry signing keys; npm has since rotated those keys, so those Corepack versions reject current pnpm releases and the Render build stops before `pnpm install`. Installing pnpm through npm avoids Corepack entirely. The version stays pinned (10.28.0, the `packageManager` field of `package.json`) and `--frozen-lockfile` keeps the dependency tree identical to `pnpm-lock.yaml`.

**Why plain `node`.** The start command runs `node dist/index.js` from `apps/backend` (the same working directory as `pnpm --filter @douala-ai/backend start`, so relative paths behave the same). It does not use the package script's `--env-file-if-exists=.env` flag: Render injects the environment variables itself and there is no `.env` file on the server. This also removes the need for Node ≥ 22.9.

`EXTENSION_ACCESS_TOKEN` is not set: the API is protected by CORS (only this extension id may call it from a browser), input validation and the rate limit (`RATE_LIMIT_MAX=60` per minute per client). `meta-llama/llama-3.3-70b-instruct:free` is not used as fallback because OpenRouter no longer offers that free variant.

### Create the service

1. https://render.com → **Get Started** / **Sign in** → *GitHub* (authorise Render).
2. Dashboard → **New +** → **Blueprint**.
3. *Connect a repository*: pick **TECHMAN237/dual-extension**. If it is not listed, click *Configure account* → GitHub → *Only select repositories* → add `dual-extension` → *Save*, then come back.
4. Blueprint name: `douala-ai`. Branch: `main`. Render reads `render.yaml` and lists the service `douala-ai-backend` (Free).
5. Fill the one field Render asks for: `AI_API_KEY` → your OpenRouter key (`sk-or-…`, from https://openrouter.ai/keys).
6. Click **Deploy Blueprint** (*Apply*). The first build takes a few minutes; the *Events* tab shows `Deploy live`.

   **Existing service created with an older `render.yaml`:** open **douala-ai-backend → Environment**, delete `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` if present, make sure `ALLOW_EPHEMERAL_STORAGE` = `true`, then *Save, rebuild and deploy* (or *Blueprints → douala-ai → Sync* to apply `render.yaml`).
7. Open the service **douala-ai-backend**: its URL is shown under the name, normally `https://douala-ai-backend.onrender.com` (Render adds a suffix such as `-x1y2` if the name is taken). Check it:

   ```bash
   curl https://douala-ai-backend.onrender.com/api/health
   ```

   Expect `"provider":"openrouter"`, `"storage":"memory"`, `"mock":false` and `"knowledgeEntries"` equal to the number of entries in `data/knowledge/douala.json`.

To change a value later: service → **Environment** → edit → *Save, rebuild and deploy*. The admin token is under the same page (`ADMIN_API_TOKEN`, *reveal*); the admin page is `https://<service>.onrender.com/admin/`.

If the deploy fails, open **Logs**: `Configuration problems:` lines name the missing or wrong variable.

### Free plan behaviour

- After 15 minutes without requests the server sleeps; the next request wakes it in about 30–60 s. The extension handles this: the popup shows **Réveil du serveur…** instead of *Offline* and keeps trying for up to 60 s; Settings → *Test connection* does the same; on the first *Translate page* it explains "Réveil du serveur, la première traduction peut prendre une minute" if nothing came back after 4 s. **Scan page** never waits for the server (language detection is local).
- 750 free instance hours per month per workspace: enough for one service running all the time.
- OpenRouter free models: 20 requests/minute, 50/day (1000/day after buying 10 credits). See `docs/AI_CONFIGURATION.md`.

### Reproducing the Render build locally

From a clean clone (no `apps/backend/.env`):

```bash
npm install -g pnpm@10.28.0 && pnpm install --frozen-lockfile && pnpm --filter @douala-ai/backend... build
cd apps/backend && AI_PROVIDER=mock PORT=10000 node dist/index.js      # development config, no key needed
curl http://localhost:10000/api/health
```

For a production-like run use `NODE_ENV=production ALLOW_EPHEMERAL_STORAGE=true AI_PROVIDER=openrouter AI_API_KEY=… ADMIN_API_TOKEN=…`. `npm install -g` may need an administrator terminal on Windows; skip it if `pnpm --version` already prints 10.28.0. `node dist/index.js` does not read `apps/backend/.env`: pass variables in the shell (or use `pnpm --filter @douala-ai/backend start`, which loads `.env`).

## 3. Extension pointing at the server

The default backend URL is compiled into the extension from `apps/extension/.env.production` (git-ignored):

```bash
cp apps/extension/.env.production.example apps/extension/.env.production
# edit it if Render gave another URL:
# VITE_DEFAULT_BACKEND_URL=https://douala-ai-backend.onrender.com
pnpm build:extension
```

The build ends with `check-build: OK (…; default backend https://…)`, which proves the URL is inside the bundle. Then `chrome://extensions` → DOUALA AI → **reload** (↻), and reload the web page.

- New installs use that URL. Installs whose stored URL is exactly `http://localhost:8787` (the old default) move to it once.
- A URL typed by hand in Settings is kept. **Utiliser le serveur par défaut** in Settings goes back to the built-in URL, and the default is not pinned in storage, so rebuilding with a new URL moves every install that uses the default.
- Without `.env.production` the build falls back to `http://localhost:8787` (development).
- CORS allows only `chrome-extension://egmamnfapihdpbmnamooaabbafmncpbh`. An unpacked extension's id depends on the folder it is loaded from: if you load `dist` from another folder (or publish to the Chrome Web Store), read the new id on `chrome://extensions` and update `CORS_ALLOWED_ORIGINS` in Render.

## 4. Development mode (local backend)

```bash
pnpm install
cp .env.example apps/backend/.env       # AI_PROVIDER=mock, or openrouter + key
pnpm dev:backend                         # http://localhost:8787 (hot reload)
```

Point the extension at it: Settings → *Backend URL* = `http://localhost:8787` → *Save settings* (or build without `apps/extension/.env.production`). The admin page is http://localhost:8787/admin/ (no token needed on localhost unless `ADMIN_API_TOKEN` is set).

## 5. Harden later

- Rotate `ADMIN_API_TOKEN` from the Render dashboard; the service restarts automatically.
- Keep `RATE_LIMIT_MAX` conservative; watch `/api/admin/usage`.
- If the API ever needs to be closed to other clients (CORS does not stop non-browser clients), set `EXTENSION_ACCESS_TOKEN` in Render and the same value in the extension Settings (*Access token*).

## Other hosts

Any Node 22 host works: build with `pnpm --filter @douala-ai/backend... build`, deploy `apps/backend/dist` together with `node_modules`, run `cd apps/backend && node dist/index.js` with the environment variables above.

## Publishing the extension

Build with the production `.env.production`, zip `apps/extension/dist` for the Chrome Web Store, then add the store extension id to `CORS_ALLOWED_ORIGINS` (comma-separated).
